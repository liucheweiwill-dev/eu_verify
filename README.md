# eu_verify

檢查 Google 回的結果，關鍵字是**真的在正文裡**，還是**只在導覽列裡**。

搭配 [eu_monitor](../eu_monitor) 用，但**刻意是分開的程式**——
eu_monitor 是單檔、零依賴、零建置的啟動器，它的價值就在於小到不會壞。
這隻工具壞掉時不應該影響你每天按的那顆鈕。
（eu_monitor 的 `docs/AGENT_BRIEF.md` §7 就是這樣規定的。）

## 網頁版現在把搜尋也包進來了

`index.html` 從上到下就是一整條流程，不用在兩個網址之間跳：

```
① 搜尋   時間範圍 + 開三個 Google 分頁（關鍵字可直接編輯）
② 收集   在三個分頁上各按一次書籤 v2（後面幾頁它自己抓，自動複製到剪貼簿）
③ 驗證   按「貼上並比對」→ 先看「收集狀況」→ 再看結果
         要把確認有命中的條列出來，按「複製正文確認清單」
```

**關鍵字不會對不起來。** ①用來搜尋的關鍵字和③用來驗證的關鍵字是同一份資料，
在頁面上改一次兩邊同時生效——整合最怕的那個 bug 在這裡結構上不可能發生。

而且 `index.html` 跟 [eu_monitor](https://liucheweiwill-dev.github.io/eu_monitor/)
**同源**（都在 `liucheweiwill-dev.github.io`，路徑不影響同源判定，2026-09-23 實測確認），
共用同一個 localStorage key `eu-nato-monitor-v2`。所以在 eu_monitor 改關鍵字，
整合版也會跟著變，反之亦然。兩個入口不會漂移。

⚠️ **①②完全不依賴 Jina**，它們只是組 Google 網址、開分頁。Jina 哪天掛了，
搜尋與收集照常能用，只有③會整批顯示「無法檢查」。

eu_monitor 維持原樣不動，它仍然是零依賴、零第三方、最不會壞的那個入口。

## 分頁：舊版書籤只收第 1 頁，而且不會告訴你（2026-09-23 發現並修掉）

Google 一頁只給 10 筆。實測 EEAS 過去一週：「約有 38 項結果」，第 1 頁 10 筆，
下面還有「1 **2** 下一頁」。書籤 v1 只讀**目前畫面上那一頁**的連結——
每站按一次，第 2 頁以後就靜默消失，驗證報告只會寫「輸入 10 筆」。

這個洞是加了驗證流程之後才出現的。原本在 eu_monitor 上是人自己看、自己翻頁，
不會漏；改成「書籤收集 → 程式驗證」之後，「按一次就收完」的錯覺讓後面幾頁不見了。
三條驗證路徑都吃書籤的輸出，所以三條都有這個洞。

### 已經關掉、不要再試的兩條路

| 想法 | 實測 | 結論 |
|---|---|---|
| 查詢加 `&num=100`，一頁顯示全部 | 照樣 10 筆、照樣要翻頁 | Google 已經不接受這個參數 |
| 三站合成一條查詢、只開一個分頁 | **約有 0 項結果** | 巢狀的 `(site:A (…)) OR (site:B (…))` 整條靜默失效，連警告都沒有——比漏抓更糟 |

### 書籤 v2 怎麼補

1. **自動翻頁**：書籤在 google.com 上執行，抓同一個查詢的下一頁是同源請求。
   每頁之間停 1.5 秒，最多自動翻 5 頁。
2. **收集紀錄**：剪貼簿裡多了幾行 `#euv v2 {...}`，記每一站收了哪幾頁、有沒有收到最後一頁、
   中間有沒有出錯。網址擷取只認 `http(s)://`，這些行不會被誤當成網址；
   `extract.js` 會把它們原樣傳下去。
3. **三條路都讀紀錄**：網頁版、`run.cmd`、GitHub Actions 的報告最上面都先講
   「收集狀況」——每站 ✓ 或 ⚠，任一站不是 ✓ 就明寫「收集不完整，下面的結果只涵蓋已收到的網址」。

「收集狀況」刻意只有兩種：確定收完（✓），以及其他一切（⚠）。
沒有紀錄（手動貼上、舊版書籤）一律算 ⚠「無法確認」——**「不知道」不能被當成「沒問題」**。
Google 真的查無結果時會標「本次查詢 0 筆（Google 顯示查無結果）✓」，
跟「沒收到這站的網址 ⚠」分開講——這就是 eu_monitor 的 AGENT_BRIEF §7
要求的「今天沒有新的」與「這次沒查成功」必須分開。

### 自動翻頁是程式代你向 Google 發查詢，要知道

第一次查詢還是你在瀏覽器裡按的；v2 只是把「下一頁」從手動點改成程式抓。
量很小（一站多 1~2 次請求），而且是你按了書籤才發生。但它**確實屬於自動查詢**，
eu_monitor 的 AGENT_BRIEF §7 把這類歸為 ToS 風險判斷——這是使用者知情後選擇的（2026-09-23）。

遇到 Google 的人機驗證頁，書籤會**立刻停下**、保留已收到的頁、在面板上寫明
「第 N 頁：Google 要求人機驗證（已停止，未繞過）」。**不會嘗試繞過。**
這時手動按 Google 的「下一頁」、在那一頁再按一次書籤，就會接回去——
紀錄會合併成「第 1–2 頁 ✓」，之前的錯誤自動清掉。

### v2 在真實 Chrome 上的驗證（2026-09-24）

開發時只能在模擬的結果頁上測（8 種情境：正常、第 2 頁被擋、加密連結、查無結果、
版面改了、超過上限、被擋後手動補收、跨分頁累積，全部通過）。沒辦法在真的 Google 上測，
因為開發用的自動化瀏覽器被 Google 當成疑似爬蟲，拿到的是**真實網址被藏起來的版本**——
結果連結是 `/goto?url=CAES…` 這種不透明 token，整頁原始碼裡找不到任何一個 eeas 網址。

2026-09-24 使用者在自己的 Chrome 上實測 EEAS（過去 24 小時）：面板寫「✓ 已收完 第 1–2 頁」，
兩頁共 17 筆，自動複製成功。**使用者的 Chrome 拿到的是一般結果連結，不是 `/goto`**——
加密連結只出現在自動化瀏覽器上。接著在網頁版按「貼上並比對」，讀剪貼簿、收集狀況、
17 筆比對都正常（這次的結果就是下面「比對規則」那兩個問題的來源）。

同一天使用者也在 consilium 與 nato 分頁上按了書籤，三站的收集狀況都是 ✓
（EEAS 第 1–2 頁 18 筆、consilium 第 1–2 頁 19 筆、nato 第 1 頁 2 筆）。
「複製正文確認清單」也在使用者的 Chrome 上實際複製、貼出成功（結尾附有未列入的筆數與收集狀況）。
整條流程——書籤收集、貼上並比對、複製清單——都已經在真實環境跑過。
萬一哪天面板寫「⚠ 加密連結」，代表 Google 對那個瀏覽器也給了那種格式，
自動收集在那種版本下做不到——面板會講實話，不會靜默少收。

### 已知的小副作用：sitelinks

Google 有時會在一筆結果底下附上同站的幾個子連結（sitelinks）。書籤會一起收進來，
它們不一定在時間範圍內。這只會讓清單多幾筆（精確度），不會漏東西（召回），所以不特別排除。

## 三種跑法，同一套判定邏輯

| | 本機版（`run.cmd`） | 網頁版（`index.html`） | GitHub Actions 版 |
|---|---|---|---|
| 要裝什麼 | Node.js 18+ | 不用裝任何東西 | 不用裝任何東西 |
| 觸發方式 | 雙擊 | 貼上、按鈕 | 開一個 GitHub issue，或在 Actions 分頁手動觸發 |
| 抓取方式 | 直接對目標站發請求 | 經第三方 [r.jina.ai](https://r.jina.ai) 中轉 | 直接對目標站發請求（GitHub 的伺服器，不受瀏覽器 CORS 限制） |
| 依賴第三方 | 不用 | **要** | 不用 |
| 結果在哪 | 開啟本機 `search_result.html` | 直接畫在同一頁 | 回覆在 issue 底下，另存一份 `latest-report.html` |
| 適合誰 | 這台電腦、能裝軟體 | 想要當場看結果 | 完全不能裝軟體、或想用手機／別人的電腦觸發 |

站台設定（`sites.json`）三邊共用同一份。判定邏輯（跟該站基準線相減）則是**兩份實作**：
`run.cmd` 與 Actions 共用 `verify.js`，網頁版在 `index.html` 裡另有一份
（`verify.js` 是 Node 腳本，瀏覽器不能直接載入）。兩份的規則必須一模一樣，
改一邊就要改另一邊——不然會漸漸分歧、結果對不上。

## 它做什麼

輸入一份網址清單，輸出一份 `search_result.html`，把每筆分成四類（依畫面上的順序）：

| | 意義 |
|---|---|
| **正文確認命中** | 關鍵字在正文裡，附上命中了哪些字、各幾次 |
| **找不到關鍵字** | Google 回了這頁，但抓到的頁面上一個關鍵字都沒有——不在正文，也不在導覽列。Google 可能是靠同義詞、詞形變化或其他語言命中的。**不是誤判，要自己看**（見下面「比對規則」） |
| **無法檢查** | 抓不到（403／逾時／網域不在設定裡），或是 PDF 檔（工具讀不了 PDF）。**既不是命中也不是未命中**。同一份理事會文件的各語言版本合併成一筆，每個語言的連結都留著 |
| **只在導覽列命中** | Google 誤判——那些字只出現在全站共用的選單裡 |

## 它不做什麼

**這是精確度工具，不是召回工具。**

它只能從 Google 已經給你的清單裡剔除假命中。
**它不會、也不可能告訴你有沒有漏掉東西**——Google 沒回的頁面它永遠看不到。

依 eu_monitor 的核心原則（漏掉比抓錯嚴重得多），這點要一直記得。

## 安裝（只做一次）

1. 裝 Node 18 以上。**零依賴，不用 `npm install`。**
2. 用瀏覽器開 `bookmarklet.html`，把上面那顆藍鈕**拖**到書籤列。

## 日常操作

```
① 在 eu_verify 網頁（或 eu_monitor）按「開啟三個分頁」
② 在三個 Google 分頁上各按一次書籤 v2 → 等面板變 ✓（後面幾頁它自己抓）
③ 回到這個資料夾，雙擊 run.cmd → 自動比對並開啟報告
```

報告最上面是「收集狀況」，先看它——任一站是 ⚠，下面的結果就不是全部。

沒有要打的指令。第 ③ 步會讀剪貼簿、寫出 `urls.today.txt`、跑比對、開啟
`search_result.html`。

面板每次點擊都會自動寫入剪貼簿（按書籤這個動作本身就是瀏覽器認可的使用者手勢，
不用再多按一下）。失敗時（無痕視窗、權限被擋）面板會用橘字說明，這時才需要手動按「複製」。

面板上的「清空」用來開始新的一輪；不清空會一直往上累加。

### 書籤沒反應的話

Google 的 CSP 有可能擋掉書籤小工具（Chrome 通常允許，但不保證）。退路：

1. 在每個 Google 結果分頁按 `Ctrl+S` 存檔
2. 把存下來的三個 `.html` 一起**拖到 `run.cmd` 上放開**

結果完全一樣。

### 手動跑

```bash
node verify.js                      # 讀 urls.txt（內含測試案例）
node verify.js my.txt -o out.html   # 自訂輸入輸出
node extract.js --text clip.txt     # 只做網址抽取，印到 stdout
```

輸入是純文字檔，一行一個網址，`#` 開頭的行會被忽略。

## 網頁版：不用裝東西，開網址就能用

`index.html` 跑在瀏覽器裡，發布在 GitHub Pages 上，而且把①②③接成一整頁
（要用之前先看下面「網頁版怎麼運作」的依賴說明）。

```
① 在這一頁上方選時間範圍 → 按「開啟三個分頁」
② 在三個 Google 分頁上各按一次書籤（自動複製）
③ 回到這一頁 → 按「從剪貼簿貼上」→ 按「開始比對」
```

結果直接畫在同一頁下面，逐筆更新，不用等全部跑完才看得到。四種分類、
判讀提醒、每個關鍵字的「命中／基準線」數字，跟本機版的 `search_result.html`
是同一套呈現。

### 網頁版怎麼運作，以及為什麼要看清楚這段再用

瀏覽器不能直接抓 eeas／nato 的頁面——**這是瀏覽器的規則，不是這幾個政府網站
特別擋的**。它們的回應沒有送 `Access-Control-Allow-Origin` 標頭，所以瀏覽器的
同源政策會擋下任何跨網域的 `fetch()`（2026-09-23 從已部署的 eu_monitor 實測
確認：`Failed to fetch`，兩站皆然）。`run.cmd`／`verify.js` 能抓，是因為
Node 腳本不受這條規則限制——CORS 管的是瀏覽器，不是「網頁」或「腳本」本身。

所以網頁版要借道一個會執行伺服器端抓取、再把結果送回瀏覽器的第三方服務。
**這代表你查的每個網址都會被那個服務看到。**

實測比較（2026-09-23，同一天測了 6 個免費 CORS 代理）：

| 服務 | 結果 |
|---|---|
| corsproxy.io | 401，已改成須付費 API key |
| api.allorigins.win | 連 `example.com` 都連不上，服務本身當時打不通 |
| api.codetabs.com | 同上 |
| thingproxy.freeboard.io | 同上 |
| proxy.cors.sh | 同上 |
| **r.jina.ai**（Jina AI Reader） | **可用**，唯一成功的一個 |

只有 [r.jina.ai](https://r.jina.ai) 這個服務能用，`index.html` 就是接它。
它預設會把頁面轉成清過的 Markdown（適合給 LLM 讀），這裡用
`X-Return-Format: html` 這個標頭要求它回傳未經摘要的原始 HTML——
**沒有這個標頭的話，判定邏輯會壞掉**，因為 Markdown 模式下某些命中的字
（連同它出現的上下文）在轉換過程會消失，基準線跟候選頁的比較基礎就不一致了。

⚠️ **這是一個你不控制的免費服務**，可能哪天就改政策、要收費、或關掉——
跟上面那張表其他 5 個一樣。它掛掉時，`index.html` 不會裝作正常：
每一筆都會誠實地落在「無法檢查」，理由會寫「無法連上 r.jina.ai」或類似字樣，
不會被誤判成「沒有命中」。看到全部都是「無法檢查」，先來檢查這裡。

不想讓任何第三方看到你查的網址，就用本機版的 `run.cmd`——它直接對目標站
發請求，不經過任何中間人。

### consilium 一樣過不去

Jina 用的是真的無頭瀏覽器抓頁面，理論上有機會騙過那個「JS 指紋挑戰」，
但實測沒有——回來的還是同一頁 `Browser check - Consilium`。跟本機版行為一致，
不算新的限制。

## GitHub Actions 版：完全不用裝軟體，也不經第三方

抓取邏輯直接重用 `verify.js`／`extract.js`，只是跑在 GitHub 的伺服器上而不是
你的電腦或瀏覽器——所以**沒有 CORS 問題**（CORS 是瀏覽器的規則，伺服器對伺服器
的請求不受它限制），也**不用經過 Jina 或任何第三方**。代價是觸發方式變成
「開一個 GitHub issue」，需要登入 GitHub 帳號。

```
① 在 eu_monitor 按「開啟三個分頁」
② 在三個 Google 分頁上各按一次書籤 → 自動複製到剪貼簿
③ 到 https://github.com/liucheweiwill-dev/eu_verify/issues/new/choose
   選「比對一批網址」，貼上（Ctrl+V），送出
④ 幾分鐘內機器人會在那則 issue 底下留言回報結果，附完整報告的連結
```

完整報告固定寫在 `latest-report.html`，網址永遠是
<https://liucheweiwill-dev.github.io/eu_verify/latest-report.html>——
每次執行都會覆蓋掉上一次的內容。要找更早的紀錄，
去[這個檔案的 commit 歷史](https://github.com/liucheweiwill-dev/eu_verify/commits/main/latest-report.html)，
每次執行都留了一筆 commit。

### 誰能觸發

**只有 repo 擁有者能觸發**，即使 repo 是公開的。這是刻意設的：
`issues` 事件在公開 repo 上任何登入的人都能發動，所以 workflow 裡用
`if:` 卡了兩個條件——開 issue 的人必須是 repo 擁有者，issue 也必須帶有
`verify-request` 標籤（用上面那個 issue 表單開就會自動帶，不用自己加）。
兩個條件都成立才會真的跑，否則任何人都能對你的 Actions 額度亂觸發。

`workflow_dispatch`（Actions 分頁那顆手動觸發鈕）本來就只有對這個 repo
有寫入權限的人才看得到、按得動，不用額外檢查。

即使真的被誤觸發，能被抓取的網址範圍還是鎖死在 `sites.json` 列的三個
網域——`extract.js` 只放行這三站（清單寫在檔案裡，要跟 `sites.json` 一致），
`verify.js` 抓取前還會再用 `sites.json` 檢查一次，issue 內文塞了什麼都跑不出這個範圍。

### 這裡也有一個容易踩到的坑，已經先避開了

Issue 內文是任何登入使用者都能打的自由文字。如果 workflow 的腳本直接把
`${{ github.event.issue.body }}` 內插進 `run:` 的 shell 指令字串裡，
內文只要含一個反引號或分號，就能在 GitHub 的 runner 上跑任意指令——
這是 GitHub Actions 最常見的注入手法之一，不是理論風險。

這裡的做法是把 issue 內文整段經由 `env:` 傳進去，腳本裡只用
`"$ISSUE_BODY"` 這種變數展開讀它，不會被當成指令的一部分解析。
已經實測驗證：貼一段刻意包含反引號、分號、`$()`、破壞引號的內文進去，
沒有任何指令被執行，內容原封不動被當成純文字寫進檔案。

## 抓到 0 筆時會停下來，不會裝作沒事

`extract.js` 抓到 0 筆會以 exit code 1 結束，`run.cmd` 收到就停住、
**不覆蓋既有的清單、不執行比對、不開報告**，並印出：

```
[STOP] No target URLs found. Nothing was run.
This does NOT mean "no news today" - it means no URLs were read.
```

這是刻意的。Google 改版會弄壞網址抽取，而「安靜地少回幾筆」正是
Google Alerts 被否決的原因（見 eu_monitor 的 `docs/AGENT_BRIEF.md` §3）。

## 為什麼不能直接 grep 網頁

**因為導覽列的字就在 HTML 裡。**

機構網站的全站選單會把國名與主題名塞進每一頁。直接搜 `Indo-Pacific`，
會在一篇完全沒提印太的人道法演說上命中——因為 EEAS 每一頁的導覽列都有
`<a href="/eu-indo-pacific-strategy-topic_en">EU Indo-Pacific Strategy</a>`。

那正是 Google 犯的錯，直接 grep 只會把同一個錯重做一次。

### 解法：跟該站的 404 頁相減

每個 host 先抓一張不存在的路徑（404 頁）。它**保證沒有正文、但有完整的導覽列**，
是最乾淨的 chrome 基準線。候選頁的命中數要**超過**基準線，才算正文真的有。

實測（2026-09-23，用當時的舊關鍵字；數字是同一個關鍵字在該頁出現幾次）：

| 關鍵字 | 候選頁 | 候選 | 基準線 | 判定 |
|---|---|---|---|---|
| `Indo-Pacific` | UN 人道法演說 | 2 | 3 | 只在導覽列 ✓ |
| `Indo-Pacific` | EEAS 印太主題頁 | 72 | 3 | 正文有 ✓ |
| `Taiwan` | UN 人道法演說 | 2 | 2 | 只在導覽列 ✓ |
| `Indo-Pacific` | NATO 印太夥伴頁 | 87 | 4 | 正文有 ✓ |

現在的預設關鍵字刻意包含導覽列裡就有的字（見下面「預設關鍵字」），2026-09-24 實測的
404 基準線：EEAS 是 Taiwan 1、China 2、Indo-Pacific 1；nato.int 是 Taiwan 1、China 3、
Indo-Pacific 1。所以「只在導覽列」是每天都會大量出現的一類——這正是相減要處理的情況。

`urls.txt` 是已知答案的測試案例，改動程式後直接跑來對（預期結果寫在檔案開頭）。

## 比對規則：什麼算「出現一次」、什麼算「找不到」

2026-09-24 拿使用者在自己 Chrome 上收到的網址（EEAS 過去 24 小時，17 筆）重跑，
發現兩個問題，當天修掉。

**1. 一個關鍵字都沒有的頁面，被標成「只在導覽列（Google 誤判）」。**
程式原本只分兩種：命中數超過基準線的是正文確認，其他一律「只在導覽列」——
包括整頁一個關鍵字都沒有的頁面。用 repo 當時的預設關鍵字（9/22 的片語版，導覽列裡都是 0 次）
重跑，那 17 筆裡有 10 筆一個關鍵字都沒有，全被說成 Google 誤判。
（使用者瀏覽器裡的關鍵字是自訂的，含 Taiwan、china；用那組跑，同樣 10 筆是真的導覽列命中。）

其中一頁是西班牙文，寫到「el cable submarino Ella」（歐洲到拉美的 EllaLink 海底電纜）。
Google 靠 cables → cable 的詞形變化命中了它，我們逐字比對找不到——兩組關鍵字下都被標成
「只在導覽列」，也不會出現在「複製正文確認清單」裡。

現在「一個關鍵字都沒有」是獨立的一類「找不到關鍵字」，跟「無法檢查」一樣標成要自己看。
工具不知道 Google 是靠什麼命中的（同義詞、詞形變化、其他語言、頁面後來改過），
**不知道就不能說是誤判**。

**2. 子字串比對會把別的字算進來。**
Coordi**nato**r、Se**nato**r、discrimi**nato**ry 裡都有 `nato`。使用者用自己的關鍵字跑出的
9 筆正文確認裡，有 3 筆是這樣來的（兩頁只寫到 Coordinator、一頁只寫到 discriminatory）。

現在的規則（網頁版與 `verify.js` 一模一樣，`keyword-test.js` 會檢查兩邊結果一致）：

- **關鍵字要從一個字的開頭算起。** Coordinator 不算 NATO；後面可以接別的字母，
  所以 drones 仍然算 drone、NATO's 仍然算 NATO。
- **以 s 結尾的關鍵字也接受單數。** cables 也算到 cable。這是猜的規則，只處理字尾的 s：
  `-ss`／`-us`／`-is` 結尾（Congress、status、crisis），或去掉 s 後不到 4 個字母的
  （news、arms）不處理，免得被砍成別的字。代價是可能多出「cable TV」這種不相關的命中——
  那是精確度的損失，換的是召回。
- 非英文的關鍵字（例如中文）不加字首限制，照舊用子字串比對。

這些規則只補得了一小部分。Google 的同義詞、其他語言、更複雜的詞形變化都比對不到——
那種頁面會落在「找不到關鍵字」，**不會被藏起來**。

### PDF 與理事會文件（2026-09-24）

網址結尾是 `.pdf` 或 `/pdf` 的，一律「無法檢查」，理由寫明是 PDF。這個工具只讀得懂 HTML，
把 PDF 當 HTML 數關鍵字，數到的是壓縮過的位元組，會被誤判成「找不到關鍵字」。

consilium 的 PDF 放在 `data.consilium.europa.eu`，這個子網域**其實沒擋程式**（curl 回 200）。
之前它們被標成「該站回 403」——理由是錯的，已經改掉。

同一份理事會文件常整批出現十幾種語言版本（2026-09-24 那輪，ST-13528-2026-INIT 一次 16 種），
都是同一份的官方譯本。現在合併成一筆，底下列出每個語言的連結——**一個連結都不丟**，
只是不用逐筆看 16 次。那一輪 consilium 的 19 個網址因此變成 4 筆。

## 預設關鍵字（2026-09-24 起）

```
EEAS、consilium： Taiwan;china;Chinese;PRC;Beijing;EU-China;Indo-Pacific;NATO;drone;cables
nato.int：        Taiwan;cross-Strait;China;Chinese;PRC;Beijing;Indo-Pacific;Asia-Pacific;South China Sea;drone;cables
```

這是使用者指定的，**刻意包含導覽列裡就有的字**（Taiwan、China、Indo-Pacific）。

9/22 曾把這些字換成片語（`Taiwan Strait`、`the Indo-Pacific`……），讓 Google 那層就能過濾——
那是召回換精確度的交易，因為當時沒辦法分辨「正文命中」和「導覽列命中」
（見 eu_monitor 的 `docs/AGENT_BRIEF.md` §10）。有了這個工具之後，使用者選擇把召回換回來：
Google 回傳幾乎所有頁面，由這裡的 404 基準線逐頁分出導覽列命中。代價是「只在導覽列」
每天會很多（2026-09-24 那輪 EEAS 18 筆裡 12 筆），那一類可以略過。

**不要以「導覽列污染」為由把這些字換回片語。** 那套方法只在使用者要 Google 那層也過濾時才適用。

`Asia-Pacific` 會帶進 `ndc.nato.int` 側欄的雜訊（AGENT_BRIEF §10「第四個陷阱」）；
AGENT_BRIEF 記錄 ndc 對 curl 回 403，所以那些頁面會落在「無法檢查」。

## 已知限制

**1. consilium 的頁面都是「無法檢查」，但原因分兩種。**
`www.consilium.europa.eu` 對所有自動化客戶端回 403（JS 指紋挑戰），連會執行 JS 的自動化瀏覽器
等 18 秒也過不去。這不是 bug，是對方擋的。只有真人手動操作的瀏覽器過得去。
`data.consilium.europa.eu` 放的是文件 PDF，沒有擋；它們落在「無法檢查」是因為讀不了 PDF（第 8 條）。

**2. 子網域有自己的導覽列。**
基準線是**按 host** 抓的，所以 `ndc.nato.int` 會用它自己的 404 頁當基準——
這是對的。但如果某個子網域擋掉 404 探測，那個 host 的結果會全部變成「無法檢查」。

**3. soft-404 會讓判定偏嚴。**
有些站對不存在的路徑回 200 加真實內容。那樣基準線會被灌水，
真命中可能被誤判成「只在導覽列」——**這個方向會漏東西**。
所以報告裡會把基準線的數字一起印出來，而且偵測到 soft-404 時會在 footer 警告。
看到警告就別信那次的「只在導覽列」分類。

**4. 只看伺服器端輸出的 HTML。**
如果某站改成用 JS 才渲染正文，這隻工具會看不到內容，把真命中判成「找不到關鍵字」
（關鍵字剛好也在導覽列裡時，則是「只在導覽列」）。
目前 eeas.europa.eu 與 nato.int 都是伺服器端輸出，沒這個問題。

**5. 預設關鍵字要手動跟 eu_monitor 同步；使用者改過的不用。**

分兩層看：

- **使用者在頁面上改的**：自動同步。兩頁同源、共用 localStorage key
  `eu-nato-monitor-v2`，在哪邊改都一樣。這層不用管。
- **檔案裡的預設值**：要手動同步。`eu_verify/sites.json` 是從
  `eu_monitor/index.html` 的 `SITES` 抄來的，那邊改了這邊要跟著改。
  兩個 repo 之間沒辦法自動同步（不合併 repo 的理由見 eu_monitor 的 CLAUDE.md）。

實務上第二層只在「全新瀏覽器、localStorage 還是空的」時才看得出差異——
一旦任一頁存過一次，存的值就會蓋掉兩邊的預設。也就是說**檔案漂移不容易被發現**，
改預設關鍵字時要記得兩邊都改。

**6. 基準線探測路徑必須固定，不能用時間戳記。**
2026-09-23 發現：EEAS 的 404 頁內容會隨探測路徑微幅變動（猜測跟「你是不是要找
這個」一類的建議連結有關），導致同一個關鍵字的基準線在不同次執行之間有 ±1 的
落差。用固定路徑重複探測同一個網址四次，結果每次完全一致——問題不是「404 頁
不穩定」，是「每次探測的網址不一樣」。`sites.json` 的 `baselineProbePath`
現在是固定字串，兩邊的程式都讀同一個值。

以今天量到的差距（真命中通常是基準線的數十倍）這個 ±1 不太可能真的翻案，
但如果哪天遇到一篇只提過一兩次的邊界案例，這個 bug 曾經真實存在過，
值得留著這段記錄。

**7. 網頁版另外依賴一個你不控制的第三方服務。**
細節、實測數字、掛掉時的行為見上面「網頁版怎麼運作」那節。本機版沒有這個問題。

**8. 讀不了 PDF。**
網址結尾是 `.pdf` 或 `/pdf` 的一律「無法檢查」，要自己開（見上面「PDF 與理事會文件」）。
只看網址判斷——結尾不像 PDF、實際卻是 PDF 的網址，仍會被當 HTML 讀、落在「找不到關鍵字」，
那一類本來就要自己看，所以不會被藏起來。

## 還沒做的：讓程式自己去 Google 查

書籤已經把「複製網址」那步解掉了，剩下的缺口是**發出查詢**——
目前還是你在 eu_monitor 按鈕、由真人的瀏覽器去查。

要讓程式自己查就得爬 Google SERP，而那會撞 bot 偵測：2026-09-22 實測，
幾分鐘內約 15 條 `site:` 查詢就被出驗證頁。每天 3 條量很低，但不構成保證，
**且不得繞過挑戰**。

所以目前這樣分工是刻意的——**每站的第一次查詢由真人發，比對交給程式**。
真人的瀏覽器有登入狀態與正常的使用節奏，不會觸發偵測；
程式只做它擅長的那半：抓頁面、數關鍵字、跟基準線比。

書籤 v2 的自動翻頁是這條線上唯一的例外（見上面「分頁」那節）：第一頁是你查的，
後面幾頁由程式抓。它守的就是下面這條硬性要求——**被擋時必須大聲失敗**，
把收集紀錄標記為不完整，絕不可以安靜地少回幾筆。

三站合成一條查詢、讓程式一次查完，實測會整條回 0 筆，不要再試。
